## Learning Tips

### Newbie Tips

如果一个合法的 HTTPS API 请求（且签名正确、Payload JSON 正确）通过 `curl` 能拿到 `200 OK`，但通过 C++ 程序却一直得到 `403 Forbidden` 并伴有 HTML（如 `Powered by Tengine`），绝大多数情况下都不是业务层鉴权报错，而是遭到了网络边缘节点或 WAF（Web Application Firewall）拦截。此时第一要排查的就是 HTTP 头里的 `User-Agent`，因为很多 WAF 会将无 `User-Agent` 视为恶意爬虫进行拦截。

### Function Explanation

`std::string::erase` 结合 `find_first_not_of` 和 `find_last_not_of` 是一种非常经典的 C++ std::string 裁剪 (trim) 范式。相较于仅仅通过业务层保证输入正确，底层的外发接口在最终组装前显式做一次 URL trim，可以最大程度上防止诸如换行、回车等幽灵字符被送进 HTTP 客户端里造成严重后果。

### Pitfalls

`cpr` 和底层 `libcurl` 对于 HTTP 请求的默认行为并不能天然满足所有 WAF 的防刷门槛。默认情况下如果没有主动塞 `User-Agent` 头部，请求很可能会在飞书之类的严苛云平台上直接碰到 403 墙。且如果传入给 `cpr::Url` 的字符串里包含了尾随换行符或空格，会导致 `libcurl` 将 URL 视为 malformed 并直接抛出 `Status: 0` 失败而不报错（或者传输出去后触发 400/403）。不要迷信框架帮你处理所有事情。
